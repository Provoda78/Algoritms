## Часть 5. Вопросы

1.  Почему Q1 (поиск по id) работает быстро даже без явного пользовательского индекса? Что такое первичный ключ и как PostgreSQL его хранит?

	Первичный ключ автоматически создаёт уникальный B-tree индекс, поэтому поиск по `id` не требует полного просмотра таблицы.

2.  Какую алгоритмическую сложность имеет Q2 (поиск по имени) без индекса? А с индексом? Объясните через структуру B+ дерева.

	Без индекса поиск требует проверить строки таблицы: `O(n)`. B+‑индекс позволяет найти диапазон за `O(log n)` и затем прочитать найденные строки.

3.  Почему Q4 (`LOWER(name) = ...`) не использует индекс по `name`? Что нужно сделать, чтобы заработало?

	Выражение `LOWER(name)` не совпадает с индексируемым столбцом `name`. Нужен функциональный индекс `CREATE INDEX ... ON employees (LOWER(name))`.

4.  В чём разница между `Seq Scan`, `Index Scan` и `Bitmap Index Scan`? Когда PostgreSQL выбирает каждый?

	`Seq Scan` читает таблицу целиком; `Index Scan` находит нужные строки через индекс; `Bitmap Scan` сначала собирает адреса строк, затем читает нужные страницы группами. Выбор зависит от доли найденных строк и стоимости чтения.

5.  Почему Q6 (`LIKE '%ван%'`) не может использовать обычный B+ индекс, а триграммный — может?

	B+‑индекс эффективно ищет по началу строки, а шаблон начинается с `%`. Триграммный индекс ищет по трёхсимвольным фрагментам внутри строки.

6.  В Q7 `status = 'active'` — это 1% строк. Почему PostgreSQL может отказаться от использования индекса? Как это связано с selectivity?

	Хотя условие выбирает лишь 1% строк, индекс может оказаться дороже, если для найденных строк нужно читать много страниц таблицы. Планировщик сравнивает эту стоимость с последовательным чтением; частичный индекс уменьшает объём индекса, так как хранит только `active`.

7.  Что означает `Index Only Scan`? Почему покрывающий индекс может дать `shared read = 0` при повторном запросе?

	`Index Only Scan` получает нужные значения из индекса без чтения строк таблицы. При повторном запросе нужные страницы могут уже быть в буфере PostgreSQL, поэтому чтений с диска (`shared read`) нет.

8.  Что такое `shared hit` и `shared read` в плане? Как они связаны с буферным пулом?

	`shared hit` — страница найдена в буфере в памяти; `shared read` — её пришлось читать с диска в буфер.

9.  Приведите пример запроса, для которого индекс не стоит создавать . Обоснуйте.

	Например, поиск по булевому столбцу, где почти все строки имеют одно значение: индекс мало сокращает выборку и может быть дороже полного сканирования.

10. В лекции мы обсуждали LSM-деревья. Для какого типа нагрузки (read-heavy или write-heavy) LSM предпочтительнее B+? Почему?

	LSM обычно предпочтительнее при `write-heavy` нагрузке: записи сначала накапливаются и сбрасываются крупными последовательными операциями. Чтения сложнее, поскольку могут проверять несколько уровней.
